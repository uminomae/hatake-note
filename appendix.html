再現ガイド

この付録について

この付録は、このサイト自体が使っている仕組み（正本のテキストファイル→生成スクリプト→無害チェック →公開用リポジトリへの反映→GitHub Pages による配信）を、読者自身のプロジェクトで再現するための ガイドである。仕組みの全体像・ディレクトリの型・運用ルール・手順までは共通部で、そのあと入口が2つに 分かれる。

  • 入口A ― 家庭菜園をそのまま模倣する: 同じ台帳構成・同じ PMBOK の語彙で自分の家庭菜園を管理したい人向け。
  • 入口B ― 別のプロジェクトへ型を写す: 家庭菜園ではないプロジェクトに、このサイトの「型」（台帳の役割・ KPI・変更ログ・教訓登録簿・リスク登録簿・品質ゲート・週次の較正）だけを写したい人向け。

名前や中身は自分のプロジェクトに合わせて置き換えてよいが、役割の分担はそのまま踏襲することを勧める。 末尾の「コピペ用プロンプト」に、共通部・入口A・入口B の3本の文面を置いた。

仕組みの全体像

  • 事実の正本（テキストファイル群）は、検索エンジンに出さない非公開のリポジトリに置く。1つの事実は 1か所にしか書かない。
  • 生成スクリプトが正本を読み、公開用のページ（HTML）を組み立てる。公開側に手書きの写しは置かない。
  • 組み立てたページは、公開してよい内容かを機械で確かめる「無害チェック」を必ず通す（読んでよい 正本の一覧＝allowlist、出してはいけない語の一覧＝denylist、の二重の網）。
  • 検査を通った生成物だけを、公開用の別リポジトリへ「毎回1コミットだけ」で置き換える（履歴を残さない）。
  • 公開用リポジトリを GitHub Pages が配信する。
  • 正本を更新して非公開リポジトリの main ブランチへ反映すると、CI（自動実行の仕組み）が生成から 公開までを一続きで行う。

ディレクトリ構成

以下は名前を中立化したテンプレート（実在のこのリポジトリの名前ではない）。役割の対応はこのサイトの 実物と同じ形にしてある。

my-note/                          … 非公開リポジトリ（正本の置き場）
├── data/                         … フラットファイルDB（1つの事実は1か所にだけ書く）
│   ├── goals.md                  … KPI の正本（目標と達成率）
│   ├── decisions.md              … 変更ログ台帳（採否と理由・追記式）
│   ├── lessons.md                … 教訓登録簿（失敗と対策・追記専用）
│   ├── trials.md                 … リスク登録簿（賭けを先に書き、結果を追記する）
│   ├── processes.tsv             … プロセス台帳（行＝データ・出典つき）
│   ├── documents-map.md          … 教科書の語彙とファイルの対応表
│   ├── todo.md                   … バックログ（時間帯ごとのバケツ）
│   └── harvest-log.tsv           … 実測ログ（予定と実績を比べる側の実績データ）
├── tools/
│   ├── build_site.py             … 正本を読んで公開ページ（HTML）を組み立てる
│   ├── safety_check.py           … 公開前ゲート（allowlist・denylist・言い換え）
│   └── publish.sh                … 生成→検査→公開用リポジトリへ単一コミットで反映
└── .github/workflows/publish.yml … 非公開リポジトリの main への反映をきっかけに検査→発行を自動実行

my-note-pages/                    … 公開用リポジトリ（生成物だけを置く・履歴を残さない）
├── index.html ／ ほか            … 生成されたページ本体
├── robots.txt                    … 検索エンジンに拾わせない設定（noindex 相当）
└── .nojekyll                     … 静的ファイルをそのまま配信させるための空ファイル

役割の要点: data/ の中身だけが唯一の正本（「本当のこと」はここにしか書かない）。tools/ の スクリプト群は、正本を読んで公開ページを組み立て、検査し、置き換えるだけの機械的な処理を担う。 公開用リポジトリ（my-note-pages/）は生成物の置き場でしかなく、自分では何も新しい情報を持たない。

ルール10箇条

  1. 正本は1か所だけに置く（同じ事実を2つのファイルに書かない）。
  2. 公開ページは全部「生成物」にする（手で書いた写しを公開側に置かない）。
  3. 読んでよい正本ファイルは一覧（allowlist＝許可リスト）で決めておく（一覧に無いものは読ませない）。
  4. 出してはいけない語も一覧（denylist＝禁止リスト）で決めておく（見つかったら公開を止める。一覧は 緩めず、代わりに元の文章の方を直す）。
  5. 内部のファイル名やパスは公開面に出さない（読者にも分かる言葉に言い換える）。
  6. 公開用リポジトリへは毎回1コミットだけで置き換える（履歴を残さない＝force-push）。
  7. 非公開リポジトリの main ブランチへ変更を反映したら、CI が検査から公開までを自動で行う （手順を人が飛ばせないようにする）。
  8. ログ・教訓・リスクの記録は追記専用にする（消さず積み重ねる）。
  9. 決めたことは理由つきで台帳に残す（あとで「なぜそうしたか」を追えるようにする）。
  10. 確認できていないことは「未確認」とそのまま書く（分からないことを分かったふりで書かない）。

再現手順

  1. GitHub のアカウントを作る（無料の範囲でよい）。
  2. 非公開リポジトリを1つ作り、上のツリーどおりに正本ファイル群を初期化する（最初は中身が薄くても、 ファイルと役割さえ決めておけば十分）。
  3. 正本を読んで HTML を組み立てる生成スクリプトを書く（言語は自由。外部ライブラリに頼らない方が、 のちのち動かす環境が変わっても壊れにくい）。
  4. 公開前に必ず通す無害チェックを書く（allowlist＝読んでよい正本の一覧、denylist＝出してはいけない 語の一覧、の二重の網）。
  5. 公開用の別リポジトリをもう1つ作り、GitHub Pages を有効にする（公開したいブランチのルートを 配信元に指定する）。
  6. 公開用リポジトリに書き込める鍵（デプロイキー）を作って公開用リポジトリ側に登録し、対になる 秘密鍵は非公開リポジトリの実行環境の「秘密変数」に登録する。
  7. 非公開リポジトリの main への反映をきっかけに、生成→無害チェック→（通れば）公開用リポジトリへの 反映、まで一続きで行う自動実行の仕組みを組む。
  8. あとは正本を書いて反映するだけの運用に入る。無害チェックで止まったら、チェックの側を緩めるの ではなく、文章の側を直す。

入口A ― 家庭菜園をそのまま模倣する

同じ領域（家庭菜園）なので、台帳の役割も語彙もほぼそのまま使える。読ませる順は次のとおり。

  1. この付録の共通部（仕組み・ディレクトリ構成・ルール10箇条・再現手順）。
  2. PMBOK 第6版 の 49プロセス表。「対応する正本・ツール」列に出てくる台帳の役割名が、 このプロジェクトが実際に持っている台帳の一覧になっている。33文書の棚卸しは「何を持ち、何を テーラリングで削ったか」の一覧。
  3. 運用記録 は変更ログ・教訓登録簿・リスク登録簿の全量＝台帳の書式の実例。
  4. アジャイル はバックログの時間帯バケツと WIP の型。

LLM に最初に求める成果物の型（付録の側で「こう返る」とは断定しない。求める形として渡す）:

  • 台帳の一覧＝役割／列（スキーマ）／追記式か上書き式か／誰が書くか（人か機械か）。
  • 最初の1週間の運用＝毎日書く台帳・毎週見直す数字。

畝の名前・品目・気象の値は読者の圃場のものに置き換える。このサイトの実データを写す必要はない。

入口B ― 別のプロジェクトへ型を写す

領域が違うので、写すのは「型」だけになる。このサイトの中身は、領域に依らない部分と家庭菜園に固有の 部分が同じ表に混ざって載っている。分けると次のようになる。

  • 領域に依らない型（写す対象）: KPI（目標と達成率）・変更ログ（採否と理由）・教訓登録簿・リスク登録簿・ バックログ（時間帯バケツ）・品質ゲート（公開前の機械検査）・週次の較正（予定と実績を並べて数字を直す）・ 「決めたことは理由つきで残す」「1つの事実は1か所」「確認できないことは未確認と書く」の運用。
  • 家庭菜園に固有の部分（写さない・自分の領域の同等物に置き換える）: 積算温度・気象の実測・畝と作土・ 輪作・播種と定植の窓・品目と品種の台帳。

読ませる順は、この付録の共通部 → 次節「型の一覧」（保証方式の7つの型＝領域に依らない骨格）→ PMBOK 第7版（原則と領域＝領域に依らない）→ PMBOK 第6版 の 33文書棚卸し（何を持ち、何を削ったか）。

LLM に最初に求める成果物の型:

  • 三列表＝ PMBOK の語彙 ｜ このサイトでの実物（役割名） ｜ 自分のプロジェクトでの対応（無ければ 「テーラリングで削る」と理由）。対象は 33のプロジェクト文書と 8つのパフォーマンス領域。
  • 最初に作る台帳5つ（KPI・変更ログ・教訓登録簿・リスク登録簿・バックログ）の列。
  • 週に1回見直す数字（KPI の実測と較正）。
  • 保証方式7つ（次節）を自分の領域で何が担うか、1行ずつ。

家庭菜園に固有の項目は、三列表の右列で「該当なし」か「代替」として現れる。それ自体がテーラリングの 実演になる（削る判断を理由つきで残すのが第7版の原則のひとつ）。

型の一覧

このサイトが 49プロセス・8領域・12原則のそれぞれに付けている「保証方式」（何がそのプロセスを 守っているか）は、7つの型に収束している。台帳の名前や畝・気象は家庭菜園に固有だが、この7つは 領域に依らない。入口B で写すのはこの表＝「人が決めて機械が検査する」分担の型である。件数は PMBOK 第6版 の49プロセス表と PMBOK 第7版 の8領域・12原則の 保証方式列を集計したもの＝「49プロセスのうち何件／8領域＋12原則のうち何件」の順（表は正本から機械で 作り直す＝手で書き換えない）。

保証方式 件数 担い手 定義 別の領域へ写すときの型
検査 13／4 機械 独立に書かれた2つの正本の数字・集合を突き合わせるスクリプト。ずれたら赤（定型ルーチン・記録時に走る） 「正本Aの数字 ⇔ 正本Bの数字」を1行で言える対を選び、機械で比べる（自分の出力どうしを比べない）
人の決裁 9／6 人 本人が理由つきで採否を決め、変更ログ台帳に1行残す。機械は判定しない 決めることの一覧（問い・選択肢・〆・答えで何が変わるか）を用意し、決裁は変更ログに理由つきで1行
正本記録 8／2 人 事実を追記専用の台帳へ書くこと自体が保証（消さない・上書きしない・過去は編集しない） 追記専用ファイルを1つ決め、日付と「事実・判断・次」だけを書く
生成器 7／4 機械 正本から表・ページを機械で作り直す。公開側に手書きの写しを持たない 「正本 → 生成物」を1行で書ける対だけ生成し、古いままの生成物を検出する検査を対で置く
テーラリング 6／0 人 持たないと決めた文書・プロセスを、理由つきで削る記録 33文書・8領域の表で「削る」に理由を1行（削った記録も台帳に残す）
発行ゲート 4／3 機械 公開・反映の直前に迂回できない機械検査（許可リスト・禁止リスト・生成物の鮮度） 公開スクリプトの入口に検査を置き、非0で止める。検査を緩めず文の方を直す
フック 2／1 機械 編集・コミットの直前直後に自動で走る小さな検査・促し（差分だけを見る） 書いた直後に差分だけ見る軽い検査を1つ置く（重い検査は定型ルーチンへ）

件数の検算: プロセス 49＝49行・領域と原則 20＝20行（この表は正本の集計＝件数と定義は生成物）。

読み方: 「担い手」が人の型（人の決裁・正本記録・テーラリング）は判断そのもの＝LLM に代行させない。 機械の型（検査・生成器・発行ゲート・フック）は、正本を2つ用意して独立に突き合わせる・正本から作り直す・ 公開の直前で止める・書いた直後に差分だけ見る、の4つの置き場の違いである。自分の領域でこの4つを どこに置くかが決まれば、道具立ての骨格は写せている。
